# 裁决、覆盖依据与失败分类

## 先判断输出可否使用

裁决器只消费当前有效尝试的已校验材料。先核对快照、目标及操作角色、动态对象、映射、契约与域版本。目标映射 ambiguous 时，保留本地观察和 mapping_ambiguous 诊断，禁止向所请求的跨位置目标签发确定标签。容量来源与目标对象不符时，核对错误发生在哪一侧：待检程序比较 peer 容量可以是待评估行为；若验证器也用 peer 容量代表 B，则验证依据失效，应退回 A2/A3 修正。已证实桩违约是案例失败；仅缺少核准依据则保留证据缺口。

## Coverage 结构

每份覆盖记录引用 domain_ref、contract_ref、target_ref、适配器版本、scope（输入、模式、路径、动态访问次数）、basis、expected_members、observed_members、missing_members、不可行成员及依据、正常见证、证明引用和结束原因。大型集合可存版本化生成器和可重放的成员索引；覆盖比较以成员身份及目标性质为准。相同输入重复出现不能补齐另一个故障模式。

| coverage_basis | 接受依据 | 何时降级 |
| --- | --- | --- |
| exhaustive_finite_domain | 实际完成且有效的成员与声明集合一致，每个输入的相关可行路径及动态访问均确定，或已覆盖全部非确定分支 | 编译配置、故障模式、路径或回访缺失，或者只比对总次数 → 覆盖不足 |
| equivalence_class_proof | 证书绑定域与性质，证明所有成员被类覆盖、同类对到达与违规性质等价；每个非空类有有效代表，证书或其核准结果可独立复核 | 只有边界样本、无等价性证明、证书过期或缺代表 → partial_sample |
| partial_sample | 登记已知见证、样本及未覆盖成员 | 有效违规见证仍可定正例；零条违规不能定反例 |

## 判定顺序

1. 输入前提、范围绑定、围栏或输出完整性失败时，先走相应的诊断和恢复。不能绕过这些条件用一条残留日志签发标签。
2. 在可接纳的结果内，至少一个符合契约的执行使请求目标出现违规，即为 positive，可提前以 witness_found 正常结束。它不要求穷尽其余输入。
3. 没有违规时，须同时具备一个正常输入下目标安全可达的见证、完整的覆盖依据，以及所有相关故障路径被阻断或仍安全的证据，才能签发 negative。所有路径都 blocked、只发生零长度空操作、只覆盖一个故障模式、声明域被截断或未证明覆盖时，均不能签发 negative。
4. 正常封存的结果仍不足以裁决时，标签为 pending，载明缺项。沿用阶段 1 的枚举，用户所称 undecided 对应这个标签。case_exec_failure 和 infra_failure 放在运行状态字段，Verdict 留空。

| 完成类别 | 例子 | 协调器动作与成本 |
| --- | --- | --- |
| completed + positive／negative | 已核准见证或完备裁决 | 走正常提交与本组揭示；B 的逻辑预算已在选择时扣减 |
| completed + pending | 正常抵达预设停止边界并封存部分覆盖，无有效违规；观测不足或目标无法唯一归属 | 作为有效完成；不自动重试。扩大域或新补证请求由本组决定并登记 |
| case_exec_failure | 案例自身无法编译、桩违反已核准前提、目标前无关错误导致终止 | 只交付案例诊断，B 的本次预算已用。修复案例产生新版本；不得自动按基础设施失败重跑 |
| infra_failure | 执行器异常退出／失租且无有效回执，工具环境临时不可用 | 按阶段 2 先查回执和发布意图，必要时废止旧尝试，同请求重新派发。只增加物理成本；超过重试上限交付诊断 |

超时按发生层级分类。计划内的观察限额有完整结束记录，可签发 pending 或使用此前已核准的正例见证；进程被强杀且没有合格回执，进入基础设施恢复。案例本身卡住且有可复核诊断则登记案例执行失败。无法判明原因时先保留运行诊断与日志，禁止推定标签。案例或基础设施失败时，早先其他已提交请求的有效见证仍保留在其原始版本下。
